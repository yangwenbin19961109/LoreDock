# ADR 0018：持久化资料索引队列与单执行器

- 状态：已接受，核心批次能力已实施
- 日期：2026-09-07

## 背景

资料上传接口此前会在同一个 HTTP 请求内完成解析、分块、向量生成和索引写入。大文件或文件夹批量导入会长时间占用请求，界面只能显示上传层面的进度；Core 退出时，运行中的任务会直接标记失败。现有 `jobs` 表已经保存来源任务、尝试次数、进度和租约，因此不应再建立一套平行任务系统。

## 决策

资料上传与索引执行拆分为两个阶段：

1. HTTP 请求完成格式、大小、内容哈希检查并保存可信原始副本。
2. 新来源与 `index_source` 任务在同一元数据事务中写入，初始状态为 `pending`。
3. API 立即返回来源和任务句柄；客户端通过现有任务读取接口观察进度。
4. Core 内只有一个资料任务执行器按创建顺序租用任务，串行执行解析、分块、Embedding 和索引写入，避免同一 SQLite 索引被多个写入任务并发修改。
5. 取消在阶段边界协作完成，不在线程或 SQLite/向量写入中强制终止。
6. Core 正常或异常退出后，未达到三次尝试上限的运行任务恢复为 `pending`；达到上限的任务明确失败，不永久停留在队列。
7. 失败和取消的任务复用可信原始副本重试，不要求用户重新选择文件。

直接调用应用服务的内部用例暂时保留同步模式，用于明确需要同步完成的内部流程和兼容性测试；公开文件与 URL 导入 API 使用后台模式。

## 一致性与并发

- 原始副本成功落盘后才创建任务，任务不会指向半写入文件。
- 单执行器限制索引写并发；搜索和删除通过索引锁与写入协调。
- 删除来源时先取消其等待或运行任务，再清理原始副本、派生产物和索引。
- 当前阶段进度值仍对应解析、分块、Embedding 和提交边界，不伪装为逐字节模型进度。
- 客户端取消已经进入解析器的任务，可能需要等当前不可中断阶段返回后才能生效。

## 分批交付

### 第一批

- 公开导入 API 后台排队。
- 单一持久化资料执行器。
- 运行任务重启恢复。
- 单任务取消和异步重试。
- 现有导入条展示“上传/入队”和“Core 索引”两个阶段。

### 后续批次

- 已完成：持久化批次实体、重复项记录与有界批次历史。
- 已完成：批次暂停、继续、取消和失败项重试。
- 已完成：应用重启后从最近批次恢复批次级 UI。
- 第二期维护项：按需增加逐条批次详情和过期历史清理；当前一期批次聚合响应保持有界。

## 结果

- 上传请求不再等待解析和索引完成。
- Core 重启不会把所有进行中导入直接变成不可恢复失败。
- 批次及条目保存在元数据库中，重复项不创建新索引任务但保留在批次统计中。
- 暂停使用明确的批次控制状态：停止租用新任务，运行项在阶段边界回到 `pending`；继续后复用同一任务和可信原始副本。
