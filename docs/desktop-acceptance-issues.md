# 桌面补齐批次验收问题

## D-A01：导入资料后切换菜单，返回知识库时资料不再显示

- 反馈日期：2026-09-04。
- 优先级：P1（高优先级），阻塞当前桌面补齐批次验收和发布；如确认原始资料或持久化记录丢失，升级为数据丢失事件处理。
- 状态：已关闭。2026-09-07 用户完成桌面人工验收并确认通过。
- 反馈时版本背景：当前代码提交为 `6b09686`，新版 Core 已启动，元数据库为 v5；这是环境记录，不代表已确认该提交或迁移导致问题。
- 用户描述：添加资料后，切换不同菜单，再切回“我的知识库”，发现刚添加的资料没有了。
- 复现步骤：在知识库添加资料 → 切换其他菜单 → 返回原知识库 → 检查资料列表。
- 预期：已导入资料仍可见、可访问；切换菜单不应删除数据，也不应错误清空列表。
- 实际：从其他菜单返回并再次选择当前知识库时，资料列表被清空后没有重新加载。
- 数据影响：本次现场只读检查确认 `app.sqlite` 与知识库索引完整性均为 `ok`，来源元数据、原件、解析产物和索引均存在，原件大小与内容哈希匹配，且无外键异常。本次实例未发生数据删除；该结论仅针对已检查的现场数据。

### 根因与修复

`selectLibrary` 会先清空资料列表，但此前只有知识库 ID、筛选、排序或分页发生变化时才触发列表请求。从收藏/最近使用等页面返回并点击已经选中的同一知识库时，ID 和默认查询状态都没有变化，React 因而不会重新执行加载 effect，空列表被保留下来。

修复后，每次用户显式选择知识库都会递增列表刷新版本并重新请求当前页；已有 `AbortController` 继续负责取消过期请求。浏览器回归已覆盖“进入收藏 → 返回同一知识库 → 原资料仍显示”，浅色与深色两种主题均通过。

### 排期与安全边界

只读现场核对、诊断、修复、自动回归和桌面人工验收均已完成，本问题不再阻塞后续开发。

诊断期间仅进行只读检查，没有删除、重导入、重建、迁移或恢复用户资料。已有元数据库备份不含原始资料副本，不能称为完整知识库备份。

### 修复验收条件

1. 使用非敏感测试资料复现并新增回归：导入后切换最近使用、收藏、Agent 连接、全部知识库及原知识库，资料仍可访问。
2. 覆盖同一知识库重复选择、跨库切换、筛选/分页、快速切换与异步请求返回顺序。
3. 比对切换前后来源 ID、元数据记录与原件，证明导航没有删除或替换资料；覆盖刷新及重启后持久化。
4. 对已有导入流程和最近使用/收藏执行回归，再由用户复验关闭问题。

### 验收结论

2026-09-07，用户在重启后的桌面开发程序中完成人工验收并确认通过。D-A01 主路径关闭；自动回归继续保护“收藏页面返回同一知识库后资料仍显示”。未单独执行的跨库、分页和快速竞态组合仍由后续完整回归持续覆盖，不将本次人工确认扩大解释为所有平台验收。

## D-A02：新建资料时缺少可见的导入进度

- 反馈日期：2026-09-07。
- 优先级：P2（重要体验问题），纳入 Phase 5 桌面验收整改。
- 状态：已关闭。2026-09-07 用户完成桌面人工复验并确认通过。
- 用户描述：新建并导入资料时没有进度条，用户无法判断上传、解析和索引是否仍在进行。
- 预期：导入开始后，在当前操作区域展示明确的单文件或批次进度、当前阶段和结果；耗时未知时使用不确定进度状态，不能伪造百分比。
- 实际：导入过程缺少持续、直观的进度反馈。

### 修复与验收要求

1. 复用 Core 已有任务状态和真实进度，不用前端计时器模拟完成比例。
2. 至少区分等待、复制/上传、解析、分块/索引、完成和失败；任务结束后提供可理解的结果。
3. 多文件导入同时展示批次总进度和当前文件状态，避免进度在任务切换时倒退或突然归零。
4. 覆盖快速小文件、较大文件、多文件、失败和重试；切换菜单后返回仍能看到未结束任务。

### 实现记录

当前 Core 导入接口会在单个文件完成解析和索引后同步返回，前端无法在请求期间轮询其内部的 25%/50%/70% 阶段。因此本批不伪造阶段百分比：单文件处理期间显示不确定进度；多文件按 Core 已确认完成的文件数推进，并显示当前文件名、批次位置、完成或失败状态。浏览器回归覆盖单文件处理中和完成状态。Core 异步化以及切换菜单后恢复进行中任务仍是后续增强边界，不在此次 UI 反馈中虚报完成。

## D-A03：HTML 搜索结果不能驱动右侧预览定位

- 反馈日期：2026-09-07。
- 优先级：P1（阻塞 Phase 5 HTML 第一批人工验收）。
- 状态：已关闭。2026-09-07 用户在全新开发进程中完成人工复验并确认通过。
- 用户描述：点击 HTML 资料的相关搜索内容后，右侧预览虽然打开资料，但不再定位到对应命中内容。
- 预期：点击任一 HTML 搜索结果后，右侧预览滚动到该结果对应的引用范围，并保持现有命中高亮行为。
- 实际：HTML 预览未跟随所点击的相关内容完成定位。

### 诊断与验收要求

1. 对照 HTML 解析产物、Chunk 的 `char_start`/`char_end`、搜索结果的 `matched_range` 与预览文本，确认偏移在哪一层失配。
2. 修复必须保留稳定引用和安全文本预览，不能通过执行原始 HTML 或模糊查找整段文本规避偏移契约。
3. 增加包含标题、实体、列表、重复文本及被排除脚本的 HTML 回归，验证多个搜索结果分别定位到正确位置。
4. 回归 Markdown、TXT、PDF、DOCX 的结果定位，避免 HTML 专项修复破坏既有格式。
5. 自动测试通过后，用真实 `.html` 和 `.htm` 文件完成桌面人工复验，再关闭问题。

### 修复记录

第一层根因是资料预览默认只读取原文前 8000 个字符，而搜索结果可能命中该窗口之外；点击结果时前端没有围绕新的 `matched_range` 重新读取原文，所以预览 DOM 中不存在对应的高亮节点。第一轮修复增加了按命中范围读取的有界上下文窗口，但 2026-09-07 用户桌面复验仍未定位。

第二层根因是同一来源切换命中时仍保留旧预览：滚动副作用在新窗口返回前已针对旧 DOM 执行，而窗口返回后资料 ID 和引用对象没有再次改变，因此没有重新滚动。第二轮修复会在每次选择引用时清除旧窗口，并让滚动副作用同时监听实际返回窗口的 `char_start`/`char_end`。真实 `.html`/`.htm` 桌面定位仍需再次复验，未据自动测试关闭问题。

第二轮桌面复验仍表现为预览闪动但未定位。诊断确认当时运行中的 Vite 开发进程仍在提供旧版 `readSource(sourceId, signal)`，没有加载新增的范围参数，因此前两次人工复验实际上始终请求字符 `0` 开始的默认窗口。停止旧进程后，使用全新 Vite 进程运行长 HTML 浏览器回归，范围请求、高亮文本和右侧滚动容器位移均通过。为防止真实网络下旧响应覆盖新窗口，预览读取同时保留单调请求序号保护。桌面程序已完整重启并确认运行时包含范围读取实现，仍需用户再次复验后关闭问题。

## 当前修复顺序

1. D-A03 已通过桌面人工复验并关闭，HTML 第一批不再受定位问题阻塞。
2. D-A02 已补齐诚实的单文件/批次进度反馈，并通过桌面人工复验关闭。

## D-A04：Core 显示已连接但首页数据请求失败

- 反馈日期：2026-09-07。
- 优先级：P1（阻塞 Phase 5 PPTX 人工验收）。
- 状态：已关闭。2026-09-07 用户在完整重启后确认验收通过。
- 用户描述：首页显示 `Failed to fetch`，左下角同时显示“Core 已连接”，已有知识库没有展示。
- 数据影响：现场只读检查确认桌面元数据库与知识库目录仍在，未执行重置、迁移或数据恢复；本次是前端加载状态错误，不是资料丢失。

### 根因与修复

桌面 Core 已进入 ready，但首批数据请求遇到瞬时网络失败时，状态同步 effect 在请求成功前就把该 Core 实例标记为“已经同步”。后续一秒轮询虽然持续看到 Core ready，却不会再次加载知识库，因此形成绿色连接状态与空白数据并存。

修复后仅在健康状态、知识库、设置和模型状态全部读取成功后记录同步完成；失败会清除同步标记并由下一轮自动重试。网络级 `TypeError` 同时改为明确的中文重试提示。Web 38 项单元测试、ESLint 和 TypeScript 检查通过，完整重启后由用户确认原有数据恢复展示。
